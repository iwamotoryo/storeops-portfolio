# API設計例（一般化）

> 本ドキュメントは、店舗業務システムを一般化したAPI設計の**例**です。本番APIのドメイン・実エンドポイント・認証情報は含めていません。パスはあくまで設計を説明するための一般的な例示です。
>
> 実案件では構成ごとにAPIの形が異なります（例：美容室・ドッグサロンは Next.js の Server Actions が中心、レンタカーは FastAPI の公開API・会員API・管理APIを分離）。詳しくは [システム構成](system-architecture.md) と各ケーススタディを参照してください。

## 設計の方針

- RESTful な設計を基本とし、リソース単位でエンドポイントを整理する
- 認証は、管理画面ではセッション（Cookie）、外部アプリ向けAPIではトークン（例：JWT）を使い分け、ログイン後の各APIを保護する
- 権限（管理者／スタッフ／エンドユーザー）に応じてアクセスできる範囲を制御する
- 入力値はサーバ側で検証し、エラーは一貫した形式で返す
- 個人情報や機微情報を含むレスポンスは、権限に応じて項目を絞る

## 共通事項

- ベースURL：`https://<api-host>/api/v1`（※ `<api-host>` は本番では非公開）
- 認証：`Authorization: Bearer <token>`
- レスポンス形式：JSON
- エラー形式（例）：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容を確認してください"
  }
}
```

## 認証

| メソッド | パス（例） | 説明 |
| --- | --- | --- |
| POST | `/auth/login` | ログイン。認証情報を受け取りトークンを発行 |
| POST | `/auth/logout` | ログアウト。トークンを無効化 |
| POST | `/auth/refresh` | トークンの再発行 |
| GET | `/auth/me` | ログイン中ユーザーの情報取得 |

※ パスワードは平文で扱わず、ハッシュ化して保存。トークンやシークレットはレスポンスや公開リポジトリに含めない。

## 顧客管理

| メソッド | パス（例） | 説明 |
| --- | --- | --- |
| GET | `/customers` | 顧客一覧の取得（検索・絞り込み・ページング） |
| GET | `/customers/{id}` | 顧客詳細の取得 |
| POST | `/customers` | 顧客の新規登録 |
| PUT | `/customers/{id}` | 顧客情報の更新 |
| DELETE | `/customers/{id}` | 顧客の削除（論理削除を想定） |

※ 個人情報を含むため、権限チェックを必須とする。

## LINE連携

| --- | --- | --- |
| POST | `/line/login` | LINEログインによる本人連携 |
